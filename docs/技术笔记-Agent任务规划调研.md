# Agent 任务规划技术方案调研笔记

> 用途：对应简历中"调研 Agent 任务规划相关技术方案，整理技术笔记"一条。
> 记录范围：2026 年 11 月，围绕"多步骤任务规划 + 工具调用"这一主题，面向个人实践项目的选型与落地。
> 说明：本文只记录方案的思想与适用场景，不转述论文中的具体实验数值，避免二手引用失真。

---

## 1. 为什么要单独做"规划"

直接把用户请求丢给大模型，得到的是**一次生成**：模型要么凭记忆答，要么编。任务一旦需要"先算再查再记"，单次生成就无法保证顺序正确、参数正确、结果可核验。

规划层的职责因此明确为三件事：

1. **拆解**：把自然语言请求变成有序的子任务；
2. **约束**：每个子任务必须落到一个已注册工具 + 合法参数上；
3. **可观测**：每一步的输入输出要能记录、能回放、能断言。

## 2. 主流方案对比

| 方案 | 核心思想 | 优点 | 主要问题 | 适用场景 |
|---|---|---|---|---|
| **ReAct**（Reason + Act 交替） | 每轮先输出思考，再决定动作，观察结果后继续下一轮 | 反馈闭环紧，能根据工具结果调整 | 每步一次模型调用，成本高；容易陷入反复试探 | 步骤数不确定、需要边做边看的任务 |
| **Plan-and-Execute**（先规划后执行） | 一次性产出完整任务列表，再逐步执行 | 调用次数少、执行路径可预览、便于审计 | 规划错则整条链路错；中途环境变化难响应 | 步骤可预判、工具固定的任务 |
| **Plan-and-Solve 提示** | 用"先制定计划再求解"的提示模板替代简单的"逐步思考" | 不改模型、零工程成本 | 只影响生成文本，不产生真正的工具调用 | 数学/推理类纯文本任务 |
| **Reflexion** | 任务失败后生成语言化的反思，带入下一轮重试 | 能从失败中改进，适合有明确成败判据的任务 | 需要额外的评估信号；重试成本高 | 可自动判分、允许多次尝试的任务 |
| **Tree of Thoughts** | 同时展开多条推理分支并搜索 | 复杂决策上探索更充分 | 调用量成倍增长，工程复杂度高 | 需要试错的规划类难题 |
| **显式 Function Calling** | 由接口层按 JSON Schema 约束模型输出工具调用 | 结构可靠，解析成本低 | 依赖厂商支持；多工具编排仍需外层逻辑 | 工具集稳定、追求稳定性的场景 |

### 选型结论

本项目采用 **Plan-and-Execute 为主 + ReAct 的观察语义为辅**：

- 规划一次产出全部子任务（省调用、路径可预览、便于前端展示"计划"）；
- 执行阶段保留 ReAct 的 Observe 语义：每步结果写入上下文，既供后续步骤复用，也作为汇总依据；
- 失败时不做整链路重规划，而是**局部重试**（参数错误/工具异常按次数重试），把复杂度和成本压在可控范围。

理由：目标任务是"杂项任务"（算数、查时间、检索、读写备忘），步骤数通常 2–5 步、工具集固定，属于 Plan-and-Execute 的典型适用区间；ReAct 的逐轮试探在这种场景下收益不足以覆盖调用成本。

## 3. 落地的四个工程难点

### 3.1 模型输出不是合法 JSON

即使提示词要求"只输出 JSON"，实际返回仍常见三类问题：

- 用 ```json 代码块包裹；
- JSON 前后夹带解释文字；
- 中途截断，括号不闭合。

处理方式（本项目 `extract_json`）：

1. 去掉代码块标记；
2. 从第一个 `{` 开始做括号配对扫描，按字符串状态位跳过引号内的括号；
3. 仍失败则带上**原始错误文本**作为反馈重新请求（最多 2 次），而不是直接抛错。

关键点：**把解析失败的信息回喂给模型**，比单纯重试更有效，因为模型能看到自己错在哪。

### 3.2 工具被"幻觉调用"

模型可能编出不存在的工具名（如 `search_web`）。处理策略分两层：

- 提示词层：把注册工具的 JSON Schema 全量注入，并给 2 组 Few-Shot 样例；
- 执行层：未注册工具**直接判失败、不重试**（重试也不会变对），并把错误写进执行记录。这样单步失败不会中断后续步骤。

### 3.3 死循环与超长任务

规划可能产出几十步甚至循环任务。用 `max_steps`（默认 8）截断执行列表：计划仍完整保留（便于排查），只执行前 N 步。这是最简单也最有效的护栏——**上限由代码控制，不交给模型自觉**。

### 3.4 上下文膨胀

如果把每步完整输出都塞回提示词，步数一多就会挤占上下文。本项目只把执行记录压缩成一行式：

```
1. calculator({"expression": "356*18"}) -> 成功: 6408
2. memo({"action": "write", "key": "product"}) -> 成功: {"product": "6408"}
```

既保留"哪一步做了什么、结果是什么"，又控制住长度。

## 4. 本项目实现映射

| 能力 | 模块 | 对应方案要素 |
|---|---|---|
| 提示词构建（工具 Schema + Few-Shot + 格式约束） | `planner.py` | Function Calling 的结构约束思路 |
| JSON 提取与结构校验 | `planner.py` + Pydantic | 输出解析层 |
| 规划失败重试（带错误反馈） | `planner.py` | Reflexion 的"反馈再试"简化版 |
| 按序执行、参数校验、失败重试 | `executor.py` | Plan-and-Execute 的执行器 |
| 上下文与观察文本 | `context.py` | ReAct 的 Observe |
| 主循环、步数上限、汇总降级 | `agent.py` | 编排层 |
| 工具注册与 Schema 生成 | `tools/base.py` | Toolformer 式"工具即接口"思路的工程简化 |

## 5. 实测记录

- 测试：`pytest` 61 个用例全部离线通过（工具 20 / 规划 12 / 执行 5 / Agent 8 / 接口 9 / 歧义输入 7），不产生真实模型调用费用。
- 离线端到端（`python examples/run_offline.py`）四类输入的表现：

| 输入类型 | 示例 | 实际表现 |
|---|---|---|
| 多步骤组合 | 算 356*18 并写入备忘 | 2 步全部成功，备忘实际写入键 `product` |
| 单工具查询 | 现在几点了 | 1 步成功，返回带时区的时间 |
| 本地检索 | onnx 是什么 | 命中内置语料并返回解释 |
| 歧义输入 | 那个东西你看着办吧 | 计划为空，返回澄清提示而非"未执行任何工具" |

### 观察到的问题

1. 规则型假模型（`OfflineDemoLLM`）只能验证链路，不能验证规划质量——真正的拆解准确率必须用真实模型 + 人工标注样本集评估，这部分尚未做。
2. 汇总阶段依赖模型，若模型忽略失败步骤会美化结果；当前只在提示词层面要求"如实说明失败"，没有做输出一致性校验。
3. 多工具依赖（后一步需要前一步的具体值）目前靠模型在规划时写死参数，缺少占位符替换机制，遇到"用上一步的结果"这类请求容易失败。

## 6. 后续可验证的方向

| 方向 | 具体做法 | 预期收益 |
|---|---|---|
| 规划质量评估 | 构造 30–50 条带标准答案的请求，人工标注期望工具序列，计算"工具序列完全匹配率" | 把"感觉能用"变成可量化指标 |
| 动态重规划 | 某步失败且错误属"参数不可用"时，只重规划剩余步骤 | 提升长任务成功率 |
| 占位符引用 | 允许 `args` 里写 `"$step1.output"`，执行时替换 | 支持跨步骤数据依赖 |
| 流式输出 | 用 SSE 逐步推送执行事件 | 前端体验从"等结果"变成"看过程" |
| 框架对照 | 用 LangGraph 复刻同一任务，对比代码量与可观测性 | 判断何时该用框架、何时该自己写 |
